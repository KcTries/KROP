# KROP 1.0 Changelog

(Formerly developed under the internal name "QOL_Realisim_Fixes" -- kept as the project's C# namespace, plugin GUID, and config filename, since that's what the saved config file is keyed by. Only the display name/DLL/plugin folder changed for release.)

## 1.0.0 (2026-08-31)

### Added
- **Enhanced NVGs.** Adds a phosphor color tint, full desaturation, screen noise, and a bloom boost on top of the game's own built-in night vision toggle -- its normal automatic exposure/bloom-threshold behavior (brightening in darker scenes) is untouched, this only layers on top of it while it's active. `Phosphor Color` (config file, default Green Phosphor) picks between the three specified colors (White `#e5f2e1`, Amber `#d39934`, Green `#4bf70c`) via a dropdown; `Noise Level` and `Bloom Level` are separate live-tunable sliders. All under a new `Enhanced NVGs` config section, with its own `Enabled` toggle. Implemented by adding `ChannelMixer` and `FilmGrain` overrides to the same Unity post-processing Volume vanilla's night vision already uses (neither previously present), and setting bloom intensity/scatter on the same `Bloom` override vanilla already owns for its own threshold control. Nothing needs to reset when night vision turns off: vanilla's own code already disables the whole Volume in that case, taking every override on it out of the render along with it.
- **First version of Enhanced NVGs had three real problems, found via testing -- fixed.** (1) The phosphor tint used `ColorAdjustments`' own Saturation + Color Filter, on the theory that setting saturation to -100 first would desaturate the scene before the color filter tinted it -- but Unity applies Color Filter (a multiply) *before* Saturation in its internal pipeline regardless of what order this code sets them, so desaturation was computing per-pixel gray from the already-tinted, still-multicolored result, reading as washed-out and barely distinguishable between phosphor colors. Replaced with `ChannelMixer`, which sums across channels (something a simple multiply can't do) to compute grayscale luminance (standard Rec.601 30/59/11 weights) times each tint channel as a single operation, with no two-step ordering to get wrong. (2) Noise barely showed up even at a nonzero intensity -- `FilmGrain.response` (left at 0.8, suppresses grain in bright areas) was suppressing almost all of it, since NVG scenes are artificially brightened by design; now 0 (uniform grain regardless of scene brightness), and swapped the fine photographic "Thin1" grain pattern for the coarser, more scintillation-like "Large02". (3) Bloom intensity had no visible effect -- root cause not confirmed; widened `Bloom Level`'s range (0-10, was 0-5) and default (3, was 1.5) and added a fixed `scatter` boost (how widely bloom spreads, not just how bright) in case the original setting was simply too subtle against an already-bright NVG scene rather than not applying at all.
- **Second round of Enhanced NVG tuning based on live testing.** `Bloom Level` confirmed working once visible -- range widened again (0-100, was 0-10) and default maxed out (100, was 3) per request. `Noise Level` removed as a config option entirely -- grain intensity is now always maxed (1.0), since a real image intensifier's scintillation isn't something you'd want dialed down for realism. Phosphor colors were still reading as too desaturated even after the ChannelMixer fix -- added a fixed +80 saturation boost via `ColorAdjustments` applied AFTER the ChannelMixer tint (safe at this stage, unlike the original ordering bug, since by this point the image has no original scene color left to muddy, just the single target hue at varying brightness -- boosting saturation here just punches up that same hue).
- **True white static/sparkle noise, replacing the film-grain look.** Unity's built-in `FilmGrain` Lookup presets (Thin1, then the coarser Large02) are all soft, even photographic film-grain patterns -- not the bright, sparse speckle a real image intensifier tube actually produces. Switched `FilmGrain` to its `Custom` texture mode, backed by a small black/white speckle `Texture2D` this mod generates and uploads itself at runtime (no art asset needed), regenerated only when its density setting actually changes rather than every frame. `Static Density` (how many specks, default 0.08 -- real sparkle is fairly sparse, not solid snow) and `Static Intensity` (how strongly it blends in, default 1, replacing the old always-maxed `Noise Level`) are both new live-tunable sliders under `Enhanced NVGs`.
- **Fixed: phosphor tint, saturation boost, and static noise all silently stopped applying after a scene/mission change**, even though `Enabled` stayed on and everything looked correct right up until the change (bloom stayed unaffected, since it wasn't cached the same way). Root cause: `ChannelMixer`/`FilmGrain` were only resolved from the post-processing Volume's profile once ever, then cached in static fields for the plugin's whole lifetime -- a scene change can rebuild that profile out from under a cached reference, so every subsequent write from this mod landed on an orphaned copy nothing renders anymore. Fixed by re-resolving `ChannelMixer`, `ColorAdjustments`, `FilmGrain`, and `Bloom` straight from the Volume's *current* profile on every call instead of caching any of them -- cheap enough to do unconditionally, and immune to the profile being swapped out from under it.
- **Fixed: white static/sparkle noise never actually appeared, at any density or intensity setting.** The generated speckle texture wrote its noise value into the RGB channels and left alpha constant at 255. Unity's own grain shader (Core RP Library's `Grain.hlsl`) reads grain luminance from the texture's *alpha* channel, not RGB, matching how Unity's own built-in grain textures are authored -- so the shader saw a uniformly opaque, zero-variance texture no matter what this mod generated, regardless of `Static Density`/`Static Intensity`. Fixed by writing the same value into all four channels, so it's read correctly whichever channel the shader actually samples.
- **Added a second, sparser "sparkle speck" noise layer on top of the fine static grain**, for the bright, distinct dots real image intensifier sparkle has in addition to fine scintillation. Composited into the same generated texture as the fine grain (FilmGrain only takes one texture map), taking the brighter of the two layers at each pixel so a speck never gets dimmed by landing on a dark grain pixel. Four new sliders under `Enhanced NVGs`: `Speck Density` (how many specks, sparser than static grain by default), `Speck Size` (in pixels, so they read as distinct dots rather than more fine grain), `Speck Intensity` (brightness), and `Speck Refresh Rate` (times per second specks re-roll to new positions). Also switched texture regeneration to a reused pixel buffer and a single reused `System.Random` (previously a new one was constructed on every regeneration, which on .NET Framework's low-resolution default seed can produce identical, repeating patterns if two regenerations land close enough together in time).
- **Fixed (attempted): sparkle specks never actually appeared, at any Density/Size/Intensity/Refresh setting.** Root cause confirmed against Unity's own URP source: `UberPostProcessPass.CalcFilmGrainParams` secretly multiplies the `Static Intensity` slider by a hardcoded 4x before it ever reaches the shader (undocumented, invisible in the Inspector), and the shader's actual blend (`Grain.hlsl`'s `ApplyGrain`) is `color + color * grain * intensity * lum` with grain remapped to [-1;1] -- so a fully-white grain pixel at Static Intensity 1 becomes a flat 5x multiply, which clips to solid white on almost any non-black scene content. Fine grain was encoded as pure 0/255 (binary), meaning it was ALREADY hitting that same clip on its bright half -- so a stamped speck block (also 0/255) was just more of the identical "clipped to white" result already scattered everywhere by the grain itself, with nothing to visually tell them apart. Narrowed fine grain's swing to a band around neutral (128 +/- 32) so it no longer clips, intending for the still-full-swing specks to be the only thing reaching pure white -- still not visible in testing, so this treated a symptom rather than the actual defect: FilmGrain and Bloom are both part of the same HDR post-process Volume stack, and there was never good reason to expect a "speck" baked into that same texture/intensity system could be made to reliably outshine the rest of the stack. Superseded below.
- **Replaced FilmGrain-based sparkle specks entirely with a Screen Space - Overlay UI Canvas.** After the above fix still didn't produce visible specks, moved the whole "distinct white dot" effect out of the post-process Volume stack altogether: a Screen Space - Overlay Canvas composites directly onto the final backbuffer *after* the camera (and its entire post-process stack, bloom included) has already resolved, so a plain white UI sprite there is guaranteed to render as opaque white regardless of tint, tonemapping, or bloom -- by construction, not by tuning. `Speck Count` (0-100, default 12) sets how many small circle sprites are drawn; `Speck Size` (1-8px) sets their diameter; each one jumps to a new random screen position every single frame (no separate refresh-rate control needed now -- there's no clipping/flicker concern this approach shares with the old one). `Speck Density`, `Speck Intensity`, and `Speck Refresh Rate` config options are gone, replaced by `Speck Count`. Repositioning a handful of small UI elements once a frame is negligible CPU cost, and since they all share one sprite/material Unity's UI batching should draw them in a single draw call regardless of count -- lighter than the texture-regeneration approach it replaces. Sorting order set to render underneath every other Screen Space - Overlay canvas (HUD, menus, mission editor UI), so it only overlays the 3D scene, not the game's own UI on top of it.
- **Toggleable NVG Auto-Gain**, replacing the game's own night vision auto-exposure entirely when enabled. Decompiled vanilla's actual `NightVision.UpdateGain()`: it only ever interpolates `postExposure`/`bloom.threshold` from the game world's time-of-day ambient light value, refreshed once a second -- it never looks at what's actually rendered, so a flare or explosion filling the frame doesn't trigger any compensation on its own. The replacement measures real rendered-frame brightness instead: an 8x8 downsample of the camera's output is grabbed via a `CommandBuffer` Blit from `BuiltinRenderTextureType.CameraTarget` inside `RenderPipelineManager.endCameraRendering`, then read back with `AsyncGPUReadback` (non-blocking -- avoids the frame stall a synchronous `ReadPixels`/`ScreenCapture` call would cause). `postExposure` is then driven toward keeping that measurement within `Min Brightness`/`Max Brightness`, at a rate of `Compensation Speed` exposure-stops/second, proportional to `Sensitivity`; `Sample Rate` controls how often the measurement itself is taken. A Harmony Prefix on `UpdateGain()` returns `false` to fully skip vanilla's method body when enabled, or `true` to let vanilla run completely unmodified when disabled -- a real toggle, not a permanent override. New `NVG Auto-Gain` config section, off by default. This is the most technically involved piece of this mod's NVG work (grabbing a camera's rendered frame outside the pipeline without a registered `ScriptableRendererFeature`) -- worth watching closely for any stutter/frame-time regression, or exposure not visibly responding to bright light sources.
- **Fixed: Auto-Gain reacted backwards** (brighter looking at a light source, dimmer looking away). Root cause: brightness was metered as a flat average across the whole downsampled frame -- a small, intense light source (a flare, a star) occupies only a few of those samples and barely moves a whole-frame average, while panning toward a large, evenly NVG-brightened patch of terrain or sky can raise the average more than the light itself did. This is the exact reason real cameras use spot/highlight metering rather than a flat average for exposure protection against bright point sources, which is what this feature is actually for. Fixed by metering off the single brightest sample instead of the average, and increasing the downsample from 8x8 to 16x16 so a small light source is less likely to be softened away entirely by the GPU's own downsampling before this mod's code ever sees it.
- **NVG toggle transition animation, precisely choreographed and with soft edges.** Entering NVG: a black bar wipes down from the top; once it fully covers the screen, two eyelid bars spawn (seamlessly matching where the single bar was), the original bar despawns, and the real NVG toggle fires at that exact moment -- the screen is still fully covered, so the swap is invisible. The eyelids then recede up/down off-screen and despawn once fully open. Exiting NVG: a black bar wipes up from the bottom; once it reaches the top, the real toggle fires underneath it, then the bar fades out over 0.5s. Every moving edge on every bar now has a soft ~80px gradient rather than a hard line, via a small feathered strip tracking each edge. Getting the choreography above required actually controlling *when* the real NVG toggle fires relative to the animation, rather than just reacting to it afterward -- vanilla flips it almost instantly on button press. `NightVisionToggleInterceptPatch` blocks `NightVision.Toggle()` (the "Night Vis" keybind's entry point) with a Harmony Prefix and re-invokes it itself once the cover animation reaches the right point; `Toggle()` is `public static` acting on a private instance field, so `Traverse` (Harmony's reflection helper) reads the current state rather than Harmony's usual `___fieldName` injection, which only works on instance-method patches. New `Transition Animation Enabled` toggle under `Enhanced NVGs`, on by default.
- **Fixed: only one of the two eyelid edges was actually soft during the opening animation.** Both eyelids' solid bars and their feathered edge strips were being created interleaved (top bar, top fringe, bottom bar, bottom fringe) -- Unity UI renders later siblings on top of earlier ones within the same canvas, and at the start of the animation each fringe sits right at screen center, exactly where the *opposite* eyelid's own solid bar also is. Since the bottom eyelid's solid bar was created after the top eyelid's fringe, it drew directly over it, hiding that gradient completely; the bottom eyelid's own fringe (created last) happened to render fine. Fixed by creating both solid bars first, then both fringes -- every fringe now reliably renders on top of every bar, not just its own.
- **Locked in NVG Auto-Gain's tuning after live testing.** `Min Brightness`, `Max Brightness`, `Sensitivity`, `Compensation Speed`, and `Sample Rate` are no longer config sliders -- they're fixed at the values settled on through testing (a fairly tight ~0.52 threshold, a slow 0.5 stops/sec ramp, sampled twice a second). `Enabled` remains a toggle. The tuned values are kept as named constants in `AutoGainConfig.cs` rather than inlined, so they're easy to find and adjust later if needed.
- **Nuclear detonation NVG flash.** When an actual nuclear detonation (not regular ordnance) goes off within the camera's view while wearing night vision, the sparkle speck count temporarily spikes and tapers back down to normal over a few seconds -- an image intensifier tube briefly overwhelmed by an intense flash, then recovering. Hooks `MushroomCloud.Start()` (the nuclear detonation's own visual effect, confirmed via decompiled source to be yield/blast-scale driven and distinct from regular Explosion effects), checks the blast position against the camera's viewport to confirm it's actually in view before triggering, then decays the extra speck count exponentially from `Detonation Speck Boost` back to the normal `Speck Count` over roughly `Detonation Taper Duration` seconds. New `Detonation Flash Enabled` toggle (on by default), under `Enhanced NVGs`.
- **Locked in the detonation flash's tuning after live testing, and removed its toggle.** `Detonation Speck Boost` (300, maxed) and `Detonation Taper Duration` (20s, maxed) are no longer config sliders -- fixed at the tested values as named constants in `NightVisionDetonationFlash.cs`. `Detonation Flash Enabled` is also gone; the effect is now always on whenever night vision is active (no separate config class left once every value was a constant).
- **AI "Parked" state overhaul.** Previously an AI aircraft in the Parked state (`PilotParkedState`) only zeroed throttle and set the brake -- now, while parked: navigation lights are forced off; the special axis (`customAxis1`, shared by swing wings/tilt rotors/VTOL engines) is held at -1 (fully down/retracted); every crew member's model is hidden (not just the flying pilot); and throttle is set to 1% rather than exactly 0 -- confirmed via decompiled source that `Airbrake.Update()` deploys the airbrakes specifically when throttle == 0f exactly and retracts them for any nonzero value, so vanilla's own exact-zero throttle was deploying the airbrakes on every parked aircraft. All undone on leaving the state.
- **Fixed: nav lights stayed on, and copilots/other crew stayed visible.** Nav lights: a parked aircraft's landing gear is already down *before* the pilot ever reaches the Parked state (it spawns that way), so the gear-extend event that forces lights on had already fired once, early, and never fired again just from sitting still -- a Prefix that only reacts to `Toggle` calls never got a chance to intercept that one call, and nothing re-invoked `Toggle` afterward for it to catch. Fixed by actively forcing every light off the moment Parked is entered (`NavLightsParkedOverridePatch.ForceAllOff`, invoking each `NavLight`'s own `Toggle(false)` via reflection directly) instead of only reacting to future calls; the reactive Prefix stays as a backstop. Crew visibility: `Aircraft.pilots` holds separate `Pilot` instances for copilot/other crew seats that don't run their own AI state machine, so only hiding the one `Pilot` whose `EnterState` fired left everyone else visible -- fixed by looping over the whole `pilots` array. The `ConditionalWeakTable` used to recover state on `LeaveState()` (which takes no parameters) is now keyed to the `Aircraft` rather than a single `Pilot`, matching the "affects the whole crew" scope.
- **Fixed: hangar door audio wasn't cockpit-filtered at all.** `Hangar`'s "moving"/open/close sounds are entirely driven by an async `UniTask` loop (`MoveDoors`), not a regular `Update()`/`FixedUpdate()` -- Harmony can't cleanly hook "once per iteration" of an async method's compiler-generated state machine the way this mod hooks `BayDoor.Update()`/`SwingWingController.FixedUpdate()` for the same kind of continuous cockpit-filtered sound elsewhere, so nothing was ever applying the filter to it. Fixed with a small dedicated driver component (`HangarCockpitFilterDriver`), added to the Hangar's own GameObject the moment its `AudioSource`s are created, that just re-applies the filter every frame for as long as the Hangar exists -- needed since cockpit-only cutoff is recomputed from live per-frame state, so a one-time application wouldn't track the player entering/leaving a cockpit correctly.
- **Fixed: turboprop turbine whine (COIN, Ci-22 Cricket) stayed unmuffled in the cockpit.** Root cause: on a turboprop, `ConstantSpeedProp`'s `propAudio` and `TurbineEngine`'s `turbineAudio` commonly share the same "engine" GameObject, and neither declared the other as an accepted sibling -- `ApplyCockpitOnlyLowpass`'s cross-contamination guard (Unity applies audio filters to a GameObject's whole combined output, not per-source) then silently skips filtering entirely on both, rather than muffling one and leaking the other. This is the exact same root cause already found and fixed once before for `JetNozzle`'s `thrustAudio`/`Afterburner` sharing a GameObject. Fixed the same way in both `ConstantSpeedPropAnimatePatch` and `TurbineEngineAnimatePatch`: each now looks up whatever `AudioSource`s actually share its own GameObject and accepts all of them as siblings (cached per-source, not rebuilt every tick), rather than needing to name the specific sibling type in advance.
- **Fixed: audible popping in the gun loop.** `AudioSource.Stop()` cuts playback instantly at whatever sample the waveform happens to be at when the burst's scheduled end arrives -- essentially never a zero crossing, so it reliably produced a click. Fixed with a short (50ms) linear fade to silence before the actual `Stop()` call, well within the existing 3-second cleanup grace window this system already had for other reasons.
- **Fixed: the pop fix above broke firing the same gun a second time.** The fade ramps the loop's `AudioSource.volume` down to 0, but nothing ever restored it afterward -- `NotifyLoopActive`'s resume path calls `.Play()` again but never touched `.volume`, so a resumed loop played back completely silent (the separate fire-end one-shot still played normally, which is why only that was audible). Fixed by recording each loop's normal volume once at creation and restoring it whenever a real shot arrives for an existing entry, resetting the fade state at the same time -- handles resuming after the fade had already finished *and* resuming partway through it, which the original fix didn't have to consider at all.
- **Lowered `ResonanceQ` (2.5 -> 1.4)** while investigating a high-pitched warble at low RPM/idle -- ruled out afterward (see below): confirmed by testing to make no meaningful difference to the warble, so it wasn't the cause after all. Left at 1.4 anyway (still a legitimate, if smaller, source of ringing against a quiet engine), but the actual fix is the Doppler one below.
- **Fixed: high-pitched engine warble at low RPM/idle, actually caused by Doppler.** Root cause, confirmed by testing: it worsened specifically while rotating the cockpit camera and held a steady (still audible) pitch once the camera stopped moving -- a cockpit camera commonly rotates around a pivot offset from the AudioListener's own position, which measurably moves the listener frame to frame even with the aircraft and its engine both completely stationary. Unity's automatic Doppler reads that rotation-induced motion as real relative velocity and pitch-shifts for it, exactly as it would for the aircraft actually moving, and a quiet/idle engine has nothing else masking the result. Fixed by computing the listener's own frame-to-frame velocity (piggybacking on the existing camera-teleport-detection tracking) and the engine clone's own velocity (already a byproduct of its position-smoothing `SmoothDamp`), then forcing `dopplerLevel` to 0 outright for that frame whenever their relative velocity is under 10 m/s -- real relative motion that slow wouldn't produce a perceptible Doppler shift anyway, so there's nothing lost by gating it out. Covers every engine type through the shared `TickEngines()` path (TurbineEngine, Turbojet, Turbofan, DuctedFan, ConstantSpeedProp).
- **Gunfire speed-of-sound delay** — gunshots (semi/burst-fire bangs, the spool-up transition, and the sustained loop sound on continuous-fire weapons) now take time to reach you based on distance, using sea-level speed of sound (340 m/s), instead of being heard instantly regardless of range. Anything within 10m of the listener plays with no delay, since that's imperceptible anyway.
- **Bullet impact speed-of-sound delay** — impact sounds (ground, armor, water, self-destruct) now use the same delay treatment as gunfire. The visual impact effect (particles, tracers) stays instant; only the sound lags behind.
- **Ejection seat speed-of-sound delay** — the rocket motor's fire sound and the canopy jettison sound are now delayed the same way.
- **Sonic boom speed-of-sound delay** — the boom itself now takes time to reach you.
- **Engine speed-of-sound delay (all engine types)** — engine sound now lags behind based on distance, continuously, for the aircraft's whole flight. Covers every engine implementation in the game: TurbineEngine, Turbojet, Turbofan, DuctedFan, ConstantSpeedProp, and PropFan.
- **Crash fireball speed-of-sound delay** — the ignition sound on a ruptured, on-fire fuel tank's fireball effect (`FuelTank.Fireball()`) now uses the same delay treatment.
- **Afterburner and thrust roar speed-of-sound delay** — `JetNozzle`'s main thrust sound and each afterburner's flame sound (separate from the turbine/prop engine hum) are now delayed the same way.
- **Countermeasure dispensing speed-of-sound delay** — the flare and chaff ejection "thump" sounds now use the same delay treatment.
- **Missile/rocket motor speed-of-sound delay** — the motor ignition sound now lags behind based on distance, continuously for the whole burn, tracking the missile in flight the same way engine sounds track their aircraft.
- **Sonic boom is now a double-crack.** A real sonic boom is two shocks (bow and tail), heard as a quick double-crack rather than a single bang — the boom clip now plays twice, ~0.1s apart, approximating that N-wave.
- **Supersonic missiles now get their own sonic boom.** `Missile` already shares the same base class the game's Mach-cone detection runs on (`Unit`), the vanilla game just never registered anything but aircraft for it — missiles are now registered too, on motor ignition. Since a missile is far shorter than an aircraft, its boom is pitched up and its double-crack gap is much tighter (~0.03s vs ~0.1s), approximating a sharp "crack" rather than a deep boom.
- **Periodic Countermeasure Release (PCR).** Toggle continuous, automatic countermeasure dispensing at a configurable interval (`Flare Release Period` in the config file, default 1.0s), so you don't have to hold the button down. Runs until toggled off or out of ammo. While PCR is active, the normal manual-fire path is locked out (a held or tapped button doesn't also fire its own separate burst on top of PCR's). While active, the HUD's countermeasure name reads "PCR" instead of the normal "Flares"/"Chaff" so it's obvious it's running. The configured period can't beat whatever hard minimum interval the aircraft's own countermeasure ejector enforces, same as vanilla's own hold-to-fire is limited today. Also added `Flare Releases Per Period` (config file, 1-5, default 1) — how many releases fire together, at once, each time the interval elapses, overriding the ejector's own cooldown between them (ammo permitting) rather than spacing them out at its normal cadence.
- **PCR now toggles via real actions in the game's own native Controls menu instead of a double-tap gesture.** The original double-tap-the-Countermeasures-button toggle made it trivial to trigger by accident while rapidly mashing Countermeasures to dump flares in a hurry. Two new actions now show up under the existing **Flight** category in the Controls menu: **`Toggle PCR`** (a direct single-key toggle, defaults to **B** on keyboard, assigned automatically the first time it's needed via Rewired's own binding API) and **`PCR Modifier`** (meant to be held alongside the vanilla Countermeasures button on controller -- Rewired's own modifier-key system only supports keyboard mappings, so this combo is checked as two separate actions rather than one native binding; ships unbound, since there's no universal default hardware element the way `KeyCode.B` works for keyboard). While the modifier is held, the normal manual countermeasure release is suppressed so that same button press never also fires a real countermeasure on top of the toggle. Both are fully rebindable from the Controls menu like any vanilla action. (A first attempt created a whole new "KQOLRF" category/tab, matching a technique the BOTE mod uses for its own custom category -- that surfaced a genuine bug in BOTE's own released input-registration code (since fixed on its `main` branch but not in any published version) that corrupted the Controls menu's layout once a second custom category also existed. Adding the actions into the *existing* Flight category instead avoids creating a new tab entirely, sidestepping the collision.)
- **PCR won't turn on while the Radar Jammer is selected.** PCR is for automatic flare dispensing, not ECM -- a toggle-on attempt while the Radar Jammer is the active countermeasure is simply rejected instead of locking onto it.
- **[FlareDiag] diagnostic logging for flare/chaff ejection speed.** `FlareEjector`/`ChaffEjector`'s ejection velocity, velocity variance, ejection interval, and grouping are all baked into each aircraft's prefab data (not literals in code), so there's no way to read their real values without asking the game directly. Logs once per ejector at spawn.
- **Flare/chaff ejection velocity is now configurable.** `[FlareDiag]` logging found vanilla's actual values ranged much wider than first seen -- 10-40 m/s depending on aircraft, and modded aircraft in the same range or higher (e.g. `Aryx_MC260_Chimera` at 35). A flat multiplier (tried first) amplifies that spread instead of closing it, turning an already-fast ejector unreasonably fast while a slow one barely catches up. Replaced with `Minimum Ejection Velocity` (config file, default 40 m/s): any ejector slower than this gets raised up to it; anything already at or above it is left untouched. Applied at spawn/rearm time, not adjustable mid-flight without one -- see the config entry's own description.
- **AeroSentry SPAAG proximity detonations now spray a narrow cone of kinetic fragments instead of a blast-radius explosion.** This 20-30mm point-defense autocannon realistically doesn't fire true blast-radius proximity rounds the way the shared `BulletSim.Bullet` code assumes every gun does. A proximity detonation from `SPAAG1` specifically now spawns a small burst of lightweight, gravity-affected kinetic fragments (default 5) angled in a narrow cone (default 1.5°) around the round's own direction of travel at the moment it detonates, each doing a fraction of the original round's pierce damage (default 50%) on a direct hit, with no blast radius of their own. Fragments are always deleted after a short lifetime (default 2s, even if they never hit anything) to keep the extra simulation cost from lingering. No dedicated impact effect on a fragment hit (vanilla's own per-gun ArmorHits assets varied too much in look to reliably reuse, and there's no mission-independent way to source a custom one) -- damage still applies normally, just without an extra spark visual. A **direct hit** from AeroSentry is completely unaffected -- it never went through `BlastFrag` in the first place, so it still applies normal damage exactly like vanilla and every other gun. Every other gun's own proximity fuse (CRAM included, all missiles, other proximity-fused shells) is also unaffected -- only AeroSentry's unit key is redirected. Fully configurable (including an `Enabled` toggle to fall back to vanilla blast-frag behavior) under `CRAM & SPAAG Proximity Fragmentation` in the config file.
- **AeroSentry's proximity detonation now fires early (`Detonate Lead Seconds`, default 0.5s).** Vanilla's own proximity fuse triggers right at the round's closest approach to its target (a one-tick lookahead on the same closing-velocity geometry check). For AeroSentry specifically, that lookahead is now widened to `Detonate Lead Seconds`, so the fragment burst goes off that much earlier along the round's flight path -- giving the fragment cone time to actually converge on the target instead of detonating right as the round is already flying past it. The burst spawns at the round's own actual position (not projected onto the target's position the way vanilla's late trigger does) so it stays visually anchored to wherever the round's tracer disappears. Approximate by nature (it assumes the target keeps flying straight for that extra window); set to 0 to fall back to vanilla's exact timing. Only affects the closest-approach trigger -- the separate unreliable-dud self-destruct path is untouched. If the round never reaches its early trigger point for some reason, vanilla's own real-time trigger still fires as a fallback and still redirects into a fragment burst, just without the lead time.
- **`Show Debug Tracers` config option** for the fragmentation feature -- when on, each fragment gets a bright orange tracer (reusing the game's own pooled bullet-tracer visual, no extra GameObject overhead) so a burst is easy to spot and confirm in-game. Off by default.
- **Landing gear fold/latch sounds and tire rolling/skid noise now covered by this mod's systems.** The gear-motor whir while it travels and the thump when it locks (`LandingGear`'s fold and latch sounds) are real mechanical events like the ejection seat rocket and weapon pylon release, so they now get the full delay + cockpit-filter treatment. Tire rolling and skid/screech noise is a continuous, physics-driven loop that starts and stops far too often (taxiing, bounces, touch-and-go) to fit the existing tracked-loop system built for a single start/stop per lifetime -- it gets cockpit-view muffling only (no propagation delay, same reasoning as the gun recoil sound above: a rolling tire is effectively co-located with the aircraft) via the same lightweight direct-on-real-source filter path, at no ongoing cost beyond the moments the gear is actually down (`LandingGear`'s own update loop already disables itself entirely once the gear is locked retracted).
- **Airbrake drag sound now gets cockpit-view muffling.** `Airbrake.airbrakeSound` is a continuous, physics-driven whoosh (volume/pitch set live from speed and how far open it is) that starts and stops as often as the pilot taps the airbrake -- same shape as landing gear's tire noise, and the same reason it doesn't fit the tracked-loop system built for a missile's one-shot flight (a quick re-open shortly after closing would fight that system's pending-stop cleanup). Gets the same treatment tire noise did instead: cockpit muffling only, applied directly to the real, live source, no propagation delay (it moves with the aircraft, not a fixed emission point).
- **Missile warhead effect audio takeover was checking for the spawned AudioSource one frame too early -- fixed.** Confirmed via the game's own asset data (IRM-S1 is internally `SAM_IR1`, a heat-seeking SAM carried by air-defense vehicles and light aircraft) that its `nearbyDetonationClip` is set (already covered by the existing flightSound-repurposing patch) and its `airEffect` VFX prefab doesn't match any of the only 21 `ExplosionAudio` components that exist anywhere in the game -- strongly indicating a plain Play-On-Awake `AudioSource`, exactly the case `MissileWarheadEffectAudioPatch` (below) was built for. But that patch was checking for it immediately after `Instantiate()`, before `Start()` runs -- vanilla's own `ExplosionAudio` sets its clip inside its own `Start()`, not at construction, so a same-shaped smaller effect doing the same thing would have had nothing to find yet. Now waits one frame (past every other script's own `Start()`, regardless of Unity's unspecified inter-script ordering within a frame) before checking.
- **Root-caused why small explosions like the smallest IR missile's warhead weren't getting cockpit filtering, even after the explosion filter fix.** `Missile.Warhead.Detonate()` spawns its own VFX prefab (one of six, depending on air/armor/terrain/water/underwater/dud) via a plain `Instantiate()` call, completely separate from both the missile-impact-clip path and the shared `ExplosionAudioManager` system already covered. Whatever plays that prefab's own detonation sound is entirely prefab-defined -- confirmed by report that the smallest IR missile reuses the same explosion asset as unguided rockets, which plausibly means a plain Play-On-Awake `AudioSource` rather than the heavier managed-explosion setup bigger warheads use. Since all six prefab-spawn branches call the identical `Instantiate(GameObject, Transform)` overload, a single transpiler swap on `Detonate()` catches whichever one actually fires: after the real instantiation, if the spawned effect doesn't already carry its own `ExplosionAudio` component (which would self-register with the already-covered system), any `AudioSource` on it gets stopped and rescheduled as a proper delayed, cockpit-filtered one-shot instead.
- **Bullet impacts on your OWN aircraft now scale cockpit muffling by how far the hit landed from the cockpit**, instead of getting the same flat cockpit cutoff every other managed sound uses. A round striking near the canopy is effectively right next to the pilot's own head and now plays close to unmuffled; one striking the tail has to "travel" back through the rest of the airframe and plays fully muffled, per the normal cockpit cutoff. Resolved per-impact via a tiny physics check centered on the exact hit point (BulletSim's own `hitInfo.point` for ground/armor hits) confirming both that a `Unit`/`IDamageable` was actually struck there and that it's specifically the local player's own aircraft (`GameManager.IsLocalAircraft`) -- impacts on anything else (enemies, terrain, water, other players/AI) are completely unaffected and keep the existing flat cockpit cutoff. Distance is measured to `Aircraft.cockpit`'s own transform, not the aircraft's root. New `Scale Own Hits By Impact Distance` (default on) and `Own Hit Full Muffle Distance` (meters, default 12 -- roughly cockpit-to-tail on a typical fighter) live under `Cockpit Filter` in the config file.
- **Per-airframe cockpit filter openings -- the UH-90 Ibis's door gun mounts leave the doors open, reducing cockpit muffling while one's fitted.** The cockpit filter previously applied the exact same cutoff to every aircraft regardless of hull integrity, but a helicopter flying with an open door (which happens whenever either door gun is mounted, not just while it's being fired) should let noticeably more outside sound in than a fully enclosed cockpit. Detected via the local player's own aircraft's actual spawned hardpoint loadout (`WeaponManager.hardpointSets[i].weaponMount.jsonKey`, which reflects the real networked loadout, not a menu-only selection) matching either door gun's mount key (`Turret_12.7mm_door`, `Turret_40mm_grenade`) on the Ibis specifically (`UnitDefinition.jsonKey == "UtilityHelo1"`). Scales the cockpit lowpass/highpass cutoffs toward fully open by a configurable fraction (`Ibis Door Gun Muffle Multiplier`, default 0.5 -- half the normal muffling) under a new `Airframe Cockpit Openings` config section, which also has its own `Enable` toggle. Built as a small per-jsonKey switch rather than a general rule framework, since this is currently the only airframe that needs one -- add a new branch if another comes up.
- **AoA buffet noise and general speed-based wind noise now get cockpit-view muffling.** `AoAFeedback` -- the vanilla aerodynamic buffet/rumble that kicks in once airspeed AND angle of attack both clear their own onset thresholds, played from a single AudioSource re-parented onto whichever aircraft's cockpit is currently flown -- and `CameraStateManager.windNoiseExternal` -- a general ambient airflow sound driven purely by velocity relative to the local air as a fraction of the speed of sound, updated every frame regardless of view state -- were both untouched by this mod before. Both get the same lightweight cockpit-only filter path used for tire noise/gun recoil/airbrake (co-located with the aircraft, so no propagation delay needed); `windNoiseExternal`'s own "External" name doesn't matter here since the filter's existing cockpit-view gate already makes it a no-op outside cockpit view.
- **Tire rolling/skid noise wasn't getting cockpit filtering on some aircraft -- root-caused.** The cross-contamination guard added earlier (to stop an unrelated sound sharing a GameObject with a filtered source from getting silently muffled too, e.g. the missile-alarm-mute bug) couldn't tell the difference between "shares a GameObject with something unrelated" and "shares a GameObject with the OTHER sound this same patch already manages" -- on any aircraft whose prefab happens to put `tireNoiseSound` and `tireSkidSound` on the same GameObject, the guard saw 2 AudioSources and skipped filtering both, permanently, for that aircraft. `ApplyCockpitOnlyLowpass` now takes an optional sibling source so a patch can vouch for a specific co-hosted source being its own; ground vehicle idle/drive engine sound (the exact same sharing risk) got the same fix, since it was equally exposed even though it hadn't been reported yet.
- **Weapon bay door and wing-sweep sounds now get cockpit-view muffling, at a reduced strength.** `BayDoor` (internal weapon bay door hinge open/close) and `SwingWingController` (variable-sweep wing drive) were both untouched by this mod before -- both get the same lightweight, no-delay, direct-on-real-source filter path already used for tire noise/gun recoil/airbrake. Landing gear's own fold/latch sound (already covered) now uses the same reduced strength too. All four -- weapon bay, gear raise/lower, wing sweep, plus the earlier gun-recoil/airbrake/tire treatment left at full strength -- reflect that a moving mechanism heard through the airframe itself isn't the same as outside air rushing past a sealed hull, so a new `Internal Mechanical Sound Multiplier` (default 0.75, under `Cockpit Filter`) scales the cockpit cutoff back toward unmuffled for just these sounds rather than applying the flat cutoff everything else uses. Engine/nacelle tilt was also requested but not found anywhere in the game's own code as a distinct sound (`TiltWingController` has no audio of any kind, and nothing else in the game references it) -- flagged for the user to confirm before assuming it's simply missing.
- **Ground vehicle engine sound (tanks, trucks, IFVs, SPAAG platforms, etc.) now goes through this mod's systems too.** `GroundVehicle` -- the single shared class for every ground vehicle, the same way `Aircraft` is for planes -- was never covered by any of the 8 aircraft engine patches, so it got instant, undelayed, unfiltered audio regardless of `Engine Sound Propagation` or the cockpit filter. Its two engine sources (idle and drive, cross-faded by speed) now get the same treatment as aircraft engines. Required widening the engine-tracking system's owner reference from `Aircraft` to the shared `Unit` base type, since `GroundVehicle` isn't an `Aircraft` but shares the same camera-detail property.
- **Fragmentation now only applies against a specific target allowlist: bombs bigger than the PAB-125, cruise missiles, and anti-ship missiles.** The fragment cone is precision-aimed at a predicted lead point, which works well against these larger, predictable threats but was whiffing against AAMs, rockets, and other small/fast/erratic missiles that vanilla's own wider blast radius already handled fine. Bomb weight doesn't track physical size cleanly (the PAB-80LR glide bomb is physically *longer* than the PAB-125 but a lighter 80kg weapon), so this is an explicit `jsonKey` list pulled from the unit definitions dump's real weights rather than a size heuristic: `bomb_250_glide` (PAB-250LR, 250kg), `bomb_250_1` (PAB-250, 250kg), `bomb500` (GPO-500, 500kg), `bomb_500_glide` (GBM-500LR, 500kg), `bomb_cluster_1` (CBO-400, 400kg), `bomb_demolition`, `bomb_penetrator1` (GPO-2P Auger bunker-buster), both `nuclearBomb1` variants, `CruiseMissile1`/`CruiseMissile20kt`, and `AShM1`/`AShM2`. Everything else -- including the PAB-125 and PAB-125HD themselves and the lighter PAB-80LR -- falls all the way back to stock vanilla behavior for that round; both the early lead-time detonation and the fragment swap are skipped, not just the fragment swap.

- **Bullet cracks.** A real supersonic bullet passing near you produces its own tiny sonic-crack shockwave, heard almost instantly -- separate from, and arriving well before, the gun's own speed-of-sound-delayed muzzle "bang" (the classic "crack-then-bang" of actually being shot at/near). Any bullet passing within 100m of the camera now triggers a short, sharp crack -- the sonic boom's own clip, reused, pitched way up (with a little per-crack pitch variation so a rapid string of them, e.g. an automatic weapon's whole burst passing by, doesn't sound like the exact same snap looping), and cut off right after it starts so it reads as a quick snap instead of a boom. Checked against the bullet's actual travel segment each physics tick (not just its position), so a fast round can't skip clean over a close pass in a single tick. Configurable (`Enable`, default on) under `Bullet Cracks` in the config file.
- **AeroSentry proximity fragmentation now also engages aircraft**, not just bombs/cruise missiles/anti-ship missiles. Checked by C# type (any `Aircraft`, covering both fixed-wing and helicopters, including modded ones) rather than a per-plane list, so it needs no maintenance as new aircraft are added. AAMs, rockets, and other small/fast/erratic guided munitions are still excluded -- vanilla's own wider blast radius already handles those fine.
- **Distance-based lowpass filtering on every delayed one-shot sound** (gunfire, bullet impacts, sonic booms, bullet cracks, ejection seat, crash fireballs, countermeasure dispensing). Real atmospheric absorption attenuates high frequencies far more than low ones over distance -- a big part of why a distant gunshot or explosion sounds duller than the same sound up close. Modeled off real absorption-coefficient data (ISO 9613-1 style tables at ~20C/70% RH) rather than an arbitrary curve: attenuation scales roughly with frequency squared, fitted to real reference points (~33dB/km at 4kHz, ~117dB/km at 8kHz) and solved for the cutoff frequency at which a given distance has attenuated a frequency band by a configurable threshold (default ~20dB). Works out to roughly 14kHz (barely touched) at 50m, ~3.1kHz at 1km, and ~700Hz (a heavily muffled rumble) at 20km by default. `Attenuation Threshold`, `Resonance`, and `Minimum Cutoff` are all live-tunable sliders under `Distance Lowpass Filter` in the config file (plus an `Enable` toggle), so the effect's intensity/harshness can be dialed in by ear in-game instead of guessing and rebuilding each time.
- **Bullet cracks now use a dedicated recorded crack sample** (embedded directly into the mod DLL, decoded at runtime by a small hand-rolled PCM WAV parser -- no Unity Editor/AssetBundle step needed for a single clip) instead of a heavily-pitched reuse of the vehicle sonic boom sound. Pitched up only modestly (1.5x base, since it's already the right kind of sound) with a little per-crack pitch variation, and cut to about half its own length so just the sharp leading transient plays. The highpass-before-lowpass filter chain from before is kept in place in case it's ever needed again, but is a no-op if the new clip's own low end is already thin.
- **Bullet crack range reduced to 50m (from 100m) and volume boosted, with bigger calibers louder still.** A crack now plays noticeably louder than before, and scales up further for bigger-caliber rounds using the same pitch/caliber curve above -- a lower (bigger-caliber) pitch means an even louder crack, since a bigger round's crack is genuinely louder in reality too (more energy in the shockwave), not just deeper. `Volume At Small Arms` and `Volume At Largest Gun` are live-tunable sliders under `Bullet Cracks` in the config file, same as the distance lowpass sliders.
- **A big enough round passing close now shakes the cockpit, not just your ears.** Any bullet crack whose caliber-scaled pitch drops below 0.5x (roughly medium autocannon and up -- a 57mm/76mm cannon sits just under this, a 105mm+ clears it) now shakes the camera via the same `CameraStateManager.ShakeCamera` vanilla's own sonic boom uses -- which already only does anything while actually in the cockpit view, so this is first-person-only for free, no separate view-mode check needed. Intensity scales with how close the pass was across the crack's own 100m range.
- **Bullet crack pitch now scales with the firing weapon's round mass ("caliber").** Bigger rounds are physically longer, and a longer round's N-wave has a correspondingly longer wavelength -- a deeper, lower-pitched crack -- the same physics already used for the missile-vs-aircraft sonic boom pitch difference. There's no explicit caliber field on a weapon's data, so this scales off `massPerRound` (a real per-gun value already present). Calibrated against real in-game values (via a one-time `[BulletCrackDiag]` dump of every gun's actual massPerRound) rather than guessed: no pitch change at .50 cal (`12.7mm Machine Gun`, 0.12kg), pitched up to 1.5x at 7.62mm-class (`Light Machine Gun`, 0.04kg), and a steady falloff down to 0.25x at the largest gun confirmed firing in-game (`155mm Railgun`, 50kg) -- interpolated in log-mass space between those three anchor points, clamped flat beyond either end.
- **Attempted: AI Search and Rescue -- reverted, not shipped in this build.** A prototype transport sub-state for AI Helo/Tiltwing pilots (Ibis/UtilityHelo1 and Tarantula/QuadTiltRotor) that would fly to, hover over, and hook up a downed friendly pilot using the game's own existing `SlingloadHook` winch mechanics. Two real bugs were found and fixed during testing (a `Vector3`/`GlobalPosition` type mismatch, and `FindHookStation` reading the wrong field -- `WeaponStation.WeaponInfo.cargo` instead of `WeaponStation.Cargo` -- which meant no aircraft's cargo hook was ever found), but the feature still never triggered in-game after both fixes, with the actual remaining cause not found before development paused. Source kept outside the project (`_Archive/SearchAndRescue/`, not compiled into this DLL) rather than deleted, in case this is picked up again later.

### Performance
- **A ship's CIWS-style automatic cannon (CRAM) firing at its real, genuinely automatic rate could tank performance -- root-caused and fixed.** A live test logged one 30mm rotary cannon triggering ~2700 bullet cracks in about 10 seconds (~250+/second at the peak) -- every individual bullet that passed within crack range independently created its own brand-new `GameObject`+`AudioSource`+filter chain, and Unity object creation/destruction at that volume is real, uncapped cost. Crack triggering is now capped to roughly 12/second globally, regardless of how many bullets qualify in the same instant -- a dense stream of rounds passing by also physically blurs into one continuous sound in reality anyway, not hundreds of overlapping discrete cracks, so this reads as more correct, not just cheaper. Confirmed via the same diagnostic logging that no other system in this mod (the gun's own bang/loop sound, the fragmentation feature) scales per-bullet the way the crack check did -- this was an isolated issue.
- **Cockpit lowpass, root-caused and rebuilt after the first version had no audible effect.** The original approach placed a filter directly on the `AudioListener`, relying on Unity applying it to the whole mixed audio scene -- but this game's own sound sources widely default `AudioSource.bypassListenerEffects` to true, meaning a listener-attached filter has no effect on almost anything regardless of how correct the cockpit-detection logic is. Rebuilt to apply the cockpit cutoff per-source instead, folded directly into the same distance-based lowpass calculation this mod's own managed sounds (gunfire, impacts, booms, engines, bullet cracks, etc.) already use -- the same mechanism already proven working. This also makes exempting cockpit UI audio (RWR warnings, missile warning tones, interface/voice/click sounds) automatic with no extra logic needed: none of that audio is played through anything this mod manages in the first place, so it was never going to be touched. `Enable` and `Cutoff` (200-20000Hz, default 8000) are live-tunable under `Cockpit Lowpass Filter` in the config file.
- **Added a configurable cockpit highpass, paired with the lowpass.** Cuts low-end rumble while in cockpit view, so combined with the lowpass it shapes a boxy, telephone-like band instead of just a dull/bassy muffle. Applied everywhere the lowpass already is -- one-shots, gun loops, engines (including the lightweight system-off path), and tracked loops. `Enable Highpass` and `Highpass Cutoff` (10-2000Hz, default 150) live under the renamed `Cockpit Filter` config section.
- **Explosion sound now gets the cockpit filter too.** Explosions (blast damage, bomb/missile impacts, etc.) turned out to go through a completely separate vanilla system, `ExplosionAudioManager`, never touched by anything else this mod does -- it already has its own independent speed-of-sound delay simulation and distance-based lowpass, so rather than duplicating that, the cockpit lowpass/highpass are now layered directly on top of whatever vanilla already correctly computes, right at the point it sets its own cutoff.
- **Cockpit muffling now fades out quickly on ejection instead of only clearing whenever the camera itself cuts away.** The camera can lag a beat behind the actual eject (the seat rides the launch rail before the view changes), and even when it does cut, jumping the filter straight from fully muffled to fully open in one frame is audible as a pop. `Aircraft.StartEjectionSequence()` -- the single choke point every ejection path runs through (keybind, radial menu, auto-eject-on-death) -- now kicks off a short 0.3s fade back to unfiltered the instant it fires. The release latches fully open once the fade finishes rather than handing control straight back to the normal cockpit-view check -- `IsInCockpitView()` can keep reporting true for a while after ejecting since the camera doesn't necessarily leave the cockpit state just because the pilot did, which first caused the fade to audibly snap back to muffled right after playing. It clears back to normal the moment the player is actually seated in a fresh cockpit again (`PilotPlayerState.EnterState`, i.e. on respawn).
- **Root-caused why the 57mm autocannon and rocket explosions were the only sounds immune to cockpit filtering, everything else was already correct.** Unity's `AudioSource.bypassEffects` flag makes it silently skip any filter component (`AudioLowPassFilter`/`AudioHighPassFilter`) sitting on the same GameObject as the source, no matter what their cutoff is set to -- and this mod's own `CopyAudioSourceSettings` helper (used to build every delayed one-shot and cloned loop) was faithfully copying that flag from whatever vanilla AudioSource it started from. The 57mm autocannon's own AudioSource ships with it set true; every other gun tested had it false by default, which is why only that one gun was unaffected. Same root cause for rocket warhead detonations specifically inside `ExplosionAudioManager` (that system's real, un-cloned source, never touched by `CopyAudioSourceSettings` at all, apparently ships the same way). All three places this mod adds filters to a source it doesn't fully own -- one-shot/loop clones, the direct-on-real-source engine cockpit-only path, and the explosion filter patch -- now force this flag off explicitly instead of inheriting it, since the whole point of attaching those filters is for them to actually run.
- **57mm autocannon still unaffected after the `bypassEffects` fix above -- second, unrelated cause found.** `Gun.ShotSound()`'s `recoilSound` (a separate mechanical action/recoil AudioSource layered under the muzzle bang) was deliberately left playing instantly and completely unfiltered on every gun, by design -- reasonable for most weapons where it's a quiet accent, but the 57mm's own audible signature turns out to be dominated by this recoil sound rather than its muzzle bang. It still plays instantly (no propagation delay -- it's effectively co-located with the platform, same reasoning as before), but now also gets cockpit-view muffling applied directly, via the same lightweight direct-on-real-source filter path used for engines.
- **Weapon pylon/bay release sound (missile launch and bomb drop) now goes through this mod's delay/cockpit-filter system too.** `MountedMissile.PlayLaunchSound()` -- the release "thump" heard when ordnance leaves the rail, shared by both missiles and bombs (bombs release via the same class's downward rail direction, not a separate one) -- explicitly set `bypassListenerEffects=true` in vanilla, which is exactly why it was never touched by anything this mod does. It's a real physical mechanical event though, not a synthesized cockpit UI cue, so it's now rescheduled as a proper delayed one-shot like everything else this mod manages.
- **Missile in-flight "whoosh" and impact sound now go through this mod's delay/cockpit-filter system too.** `Missile.flightSound` is a separate AudioSource from the motor's own (already handled) -- it's continuously pitched/volumed by live speed while in flight, then repurposed at detonation to play the actual impact clip once. Neither path was touched by this mod before. The flight whoosh is now a proper tracked loop (with live pitch/volume pass-through added to that system specifically for this, since the existing missile-motor use case never needed it), and the impact sound is rescheduled as a real delayed one-shot instead of playing instantly.
- **Cockpit lowpass default cutoff lowered from 8000Hz to 3000Hz -- confirmed via diagnostic logging that the system itself was working correctly all along, just imperceptibly subtle at the old default.** Engine hum, explosions, and gunfire are mostly well under 5kHz already, so a filter only touching content above 8-10kHz barely removes anything audible. Real speech intelligibility lives mostly in 300-3400Hz (telephone bandwidth), which is roughly where a "muffled through a wall/helmet" effect actually needs to cut in to read as muffled rather than a faint treble dip. Note: this only changes the default for a fresh config file -- anyone who already saved a `Cutoff` value keeps it and needs to lower it manually in ConfigManager.
- **Engine sound now gets cockpit muffling even with `Engine Sound Propagation` left off.** That toggle guards the expensive part of engine audio (the continuous distance-delay history/smoothing/clone tracking), but cockpit-view muffling alone is cheap and shouldn't require paying for that just to get it. Every engine-type patch's own "system off" fallback path (which normally lets vanilla's instant, undelayed audio play untouched) now also applies just the cockpit lowpass directly to the real, live engine AudioSource -- covers every engine type (TurbineEngine, Turbojet, Turbofan, DuctedFan, ConstantSpeedProp, PropFan, JetNozzle thrust, and afterburners).
- **Bullet cracks no longer trigger from the player's own outgoing rounds while in cockpit view.** There's no "near miss" experience for the shooter -- that's just their own gun going off right next to their ear. Scoped to cockpit view specifically; external/free-cam view is unaffected.
- **Distance-based lowpass now also applies continuously to missile/rocket motor sound**, updated live every frame the same way gun loops and engines already are -- a fast-moving source like a missile in flight needs its cutoff recomputed continuously as distance changes, not set once like a stationary one-shot.
- **Distance-based lowpass now also applies continuously to gunfire loops and all engine/afterburner audio**, not just one-shot sounds. As a firing gun or a running engine moves farther from the camera, its sound now progressively muffles in real time (re-evaluated every frame from live distance), the same physically-grounded curve as the one-shot filtering above. Cheap to add: it's a single extra scalar property write per active loop/engine per frame, in the same category of cost as the pitch/volume/doppler updates engines already do every frame (not a per-frame settings/curve copy, which is the kind of thing that actually shows up on a profiler).

- **Lifeboats floating high above the water after the camera looked away and back, root-caused and fixed.** `LifeboatBob`'s gentle bobbing motion cached the boat's Y position in WORLD space at spawn and reapplied it every frame -- the boat itself is correctly parented under `Datum.origin` and would normally follow the game's periodic floating-origin re-centering automatically, but this fought that every frame by resetting the world Y back to its stale pre-shift value, permanently pinning the boat to its old altitude the moment any origin shift happened while it wasn't being watched (reported: boats found floating ~100m in the air after the camera returned). Same category of bug as the earlier engine-audio-history floating-origin fix -- switched to caching/applying the bob in LOCAL space instead, which Unity automatically keeps correct across an origin shift with no extra bookkeeping needed.
- **Purely kinetic rounds (e.g. railgun penetrators) no longer act like proximity-fused shells against soft targets.** Vanilla assigns a bullet's proximity fuse purely from the TARGET's armor tier, completely independent of whether the firing weapon actually has any blast damage to detonate -- a genuinely kinetic round (0 blast damage) fired at a lightly-armored target still got flagged with a proximity fuse, sending it through the same "detonate near the target" logic as a real explosive shell and ending its flight early instead of letting it fly straight through like a real kinetic penetrator would (harmless damage-wise either way, since the "detonation" dealt 0 damage regardless, but visibly wrong). Fixed generally by weapon data (any weapon with 0 blast damage), not scoped to one gun by name, so it covers every kinetic-only weapon in the game the same way.

### Fixed
- **Misdiagnosis, corrected: "some missile/rocket motor effects stayed visible after impact" was never this mod's bug.** Spent several rounds restructuring `MissileWarheadEffectAudioPatch`'s one-frame-delayed audio takeover (routing it through this mod's driver, then a per-frame queue, then a dedicated coroutine host) on the theory that attaching a component to the just-spawned warhead VFX instance was interfering with a Unity `ParticleSystem`'s own "Stop Action: Destroy" cleanup. None of those rewrites actually fixed the reported symptom, and one of them broke warhead-impact sound filtering/delay as a side effect. Root cause, found by the user via direct testing: a completely unrelated third-party mod adds ambient lights to rocket motor effects, and that addition is what was making them stick on -- nothing to do with this mod's code at all. Reverted `MissileWarheadEffectAudioPatch` to its original, simplest form (a one-shot `DelayedWarheadAudioTakeover` component on the spawned instance, waiting one frame before checking for a Play-On-Awake audio clip) and removed the now-unused driver/queue/coroutine machinery this misdiagnosis had added to `SoundPropagation.cs`. Sound filtering/delay for warhead impact effects is unaffected by any of this -- it was never actually broken by the original design, only by one of the intermediate "fixes" for the unrelated bug, which is also reverted.
- **Landing gear fold sound (the motor whir while the gear travels) sounded like it got "left behind" and faded out with distance -- root-caused.** It was routed through `ScheduleDelayedOneShot`, which spawns its clone at a fixed point in space and never moves it again -- correct for a genuinely instantaneous event (a gunshot's sound doesn't follow the shooter after it fires), but wrong for a sound that plays continuously for several seconds while the emitting aircraft keeps flying: the clone stayed frozen at wherever the aircraft was the instant the gear started moving, and by the time the multi-second clip finished, the (real, still-flying) aircraft could be well away from it. Vanilla's own `LandingGear_OnSetGear()` was already playing this correctly on the real, live, moving `AudioSource` before this mod's Postfix ever ran -- the old code then threw that away (`Stop()` + a frozen clone) purely to get the cockpit-filter treatment, for a propagation delay that was always ~0 anyway (landing gear is always within near-field range of the listener). Now left playing on the real source and filtered in place every tick it's actually playing, the same lightweight pattern already used for tire noise/airbrake -- it tracks the aircraft for free since Unity does that automatically for any live, unstopped `AudioSource`. The latch thump (the short click when the gear locks) was unaffected -- genuinely brief enough that a frozen emission point was never perceptible -- and still uses the delayed-one-shot path.
- **Resonance-ringing bug (previously fixed for PropFan at low RPM) recurred intermittently, described as a warble that changed with camera/view state -- root-caused as a gap in the original fix, not a regression.** `LowpassResonanceFor`/`HighpassResonanceFor` decide whether to apply the boosted resonance value by checking if a computed cutoff is still exactly at the filter's own "fully open" edge (22000Hz / 10Hz) -- a strict comparison that assumes that value is always bit-exact. Cutoffs reaching that check are now frequently the result of several chained `Mathf.Lerp` blends (own-hit distance, internal-mechanical multiplier, ejection-release fade, airframe-opening multiplier) layered on top of each other depending on what's happening that frame -- landing a fraction of a Hz short of the exact edge on some blend combinations was enough to flip the check back to "actively cutting," reintroducing the exact same audible ring the original fix eliminated, just intermittently and tied to whichever combination of blends a given frame's camera/view state produced instead of constantly. Both functions now use a small (1Hz) tolerance around the edge instead of an exact comparison.
- **Root-caused the "cockpit filter doesn't reapply" report, and it wasn't about camera state at all -- it was a consistent bug on any afterburner-equipped jet, confirmed via `[CockpitFilterShareDiag]` logging `'nozzle'` being skipped.** `JetNozzle.thrustAudio` and each `Afterburner.source` are both `[SerializeField]` fields baked into the aircraft's prefab -- meaning they're co-located on the same `'nozzle'` GameObject from the moment the aircraft spawns, not something that starts safe and later becomes unsafe. The cross-contamination guard's original "cache the safety verdict forever, the first time this source is checked" design meant whichever one got checked first would (correctly) find the other and mark itself unsafe -- permanently, even though both are sounds this mod already manages. This wasn't camera-cycling-dependent; it was present on any such aircraft the whole time `Engine Sound Propagation` is off (this user's own config). The same log also caught the identical problem for a gun's `recoilSound` sharing a GameObject with its own `sources[]` (confirmed on the Ibis's 40mm GMG turret specifically) -- harmless to co-filter since `sources[]` never actually plays on the real AudioSource once `Gun.ShotSound()` is fully replaced by this mod's own Prefix. Fixed two ways: (1) `ApplyCockpitOnlyLowpass` now re-evaluates the safety check every call instead of locking in a verdict forever, so a source whose sibling hasn't been created/registered yet can still self-heal once it does (only matters for cross-patch cases; costs one cheap `GetComponents<AudioSource>()` per call for sources that are never accepted, e.g. AoA feedback and wind noise, which genuinely do share with unrelated vanilla audio and correctly stay skipped); (2) `JetNozzleAudioEffectsPatch` now declares thrustAudio and every afterburner source as accepted siblings of each other (handled centrally there, not split with `JetNozzleAfterburnerPatch`, since `Thrust()` always calls `AudioEffects()` before any `Afterburner.Run()` and an `Afterburner` has no back-reference to look thrustAudio up the other way), and `GunShotSoundPatch` now declares a gun's own `sources[]` as accepted siblings of its `recoilSound`. The unsafe-skip log itself is also now logged once per source instead of every time it's rechecked, to match the new re-evaluate-every-call behavior without spamming.
- **AoA buffet-noise cockpit filter patch (added this same round) never actually applied -- Harmony refused to patch it at all.** The Postfix asked Harmony to inject a private field named `source` via `___source`, but `AoAFeedback`'s real field is `_source` (leading underscore) -- Harmony's injection convention matches the parameter name after its own triple-underscore prefix against the field name literally, so this needed a 4th underscore (`____source`). Confirmed via `BepInEx/LogOutput.log` and Unity's own `Player.log`: `[Error : HarmonyX] Failed to patch ... No such field defined in class AoAFeedback`, caught internally by Harmony's `PatchClassProcessor` and logged rather than thrown further -- confirmed via the same logs that this was an isolated failure (no other patch in this mod failed to apply, and no runtime exceptions occurred), not a wider breakage of the whole cockpit filter system.
- **Three unbounded memory leaks found and fixed via a full-codebase quality pass.** `CramProximityFragmentPatch`'s and `TurbineEngineAnimatePatch`'s own log-dedupe collections, and `SonicBoomManagePatch`'s retrigger-cooldown tracker, all used a plain `HashSet`/`Dictionary` keyed by an object (a bullet, an engine, an AudioSource) that's created and destroyed constantly during play, with no cleanup path at all -- not per-object, not even on mission end. The CRAM one was the worst: a single CIWS-style rotary cannon burst was independently measured elsewhere in this mod at ~2700 qualifying bullets in 10 seconds, meaning that dictionary could grow into the tens of thousands of permanently-retained objects within one engagement. All three now use a `ConditionalWeakTable`, the same fix `BulletCrackPatch`'s own bullet-dedup collection already used for the identical reason -- these three files just hadn't been updated to match.
- **A fragile single-shot `Stream.Read()` in the lifeboat model loader could silently truncate the embedded AssetBundle.** `Stream.Read` isn't guaranteed to fill the requested buffer in one call; the same fragility was already fixed with a proper read loop in the newer `BulletCrackAssets` embedded-resource loader, but the older, larger lifeboat model load was never updated to match. Now uses the same read-loop pattern.
- **Lifeboats could spawn a second full batch for the same ship** if its sync'd "disabled" state ever re-triggered the spawn hook (e.g. a late network resync) -- added a per-ship guard so a ship only ever gets one wave of lifeboats.
- **Doppler effect restored on moving delayed sounds.** Every delayed clone was hardcoding no Doppler shift at all, which is correct for one-shot sounds that don't move once emitted (matching how vanilla's own explosion audio behaves) but was incorrectly silencing Doppler on the continuously-moving engine and gun-loop sounds too, where the base game normally applies it. Engine/afterburner/thrust sounds now carry their own Doppler value (including JetNozzle's camera-facing-dependent value) through the delay system frame by frame; one-shot sounds are unaffected and still have no Doppler shift, as before.
- **A stale-position bug from the game's floating-origin re-centering was found and fixed** (engine sounds' 30-second position history was stored as raw world coordinates that didn't follow scene re-centers, unlike a live GameObject's position) — this was a real bug, but testing afterward showed it was not the (or not the only) cause of engine volume not responding to distance. That issue is still open; see Known issues.
- **Automatic weapon spool-up sound no longer repeats mid-burst.** A brief gap between shots (frame timing, the game's own bullet-queue jitter) could fully remove a still-firing weapon's tracking entry, making the very next shot look like the start of a whole new burst and replay the spool-up bang. Loop entries now stay alive for a few seconds after their audio actually goes quiet, so a shot arriving shortly after a brief gap resumes the same loop instead.
- **Sounds beyond 20km are no longer tracked at all**, engine sounds additionally being dropped if they drift past that range mid-flight — avoids wasting per-frame work (engines especially, which keep a rolling history for as long as the aircraft is alive) simulating something nobody will ever hear.
- **Engine sound volume not responding to distance, root-caused and fixed.** The clone only ever copied the real engine's AudioSource settings (spatialBlend, min/maxDistance, rolloff curve) once, at creation. Those settings can end up different depending on the exact frame a clone happens to be created on — e.g. one caught right as `Aircraft.SetCockpitRenderers()` fired had its engine's AudioSource briefly unparented with spatialBlend forced to 0 (fully 2D, no distance attenuation at all), a transient spawn/init state the game corrects a moment later without ever touching the audio clip, which was the only thing the old re-sync check watched for. Settings now re-sync from the real source every frame instead of only when the clip changes.
- **Doppler warbling on engine sounds fixed.** Unity's automatic Doppler infers velocity from how fast an AudioSource's own position changes frame to frame. The engine clone's position comes from a 30-second history buffer, re-sampled every frame at "now minus however long the sound currently takes to arrive" — since that delay is itself recalculated from live distance each frame, the sampled point in history advances faster or slower than real time as the listener's distance opens or closes, producing a noisy position signal that read as pitch warbling. The clone's position now smooths toward that sampled target instead of snapping to it exactly, giving Unity a clean signal to compute Doppler from.
- **Missile/rocket motor sound now stops with the same delay treatment as everything else**, instead of cutting out instantly the moment the real motor burns out or the missile is destroyed. A distant listener now hears the motor's tail end arrive late, same as the gun loop's spool-down. Also added a safety clamp (shared with the gun loop) so an extreme closing speed can compress a burst's apparent duration all the way to zero but never past it into "heard the end before the beginning."
- **Engine audio no longer audible before a supersonic aircraft actually arrives.** The delay/340 formula only holds up for a source closing slower than the speed of sound; once closing speed goes supersonic, the naive calculation would try to advance the engine's history-playback point faster than real time, run past "now," and get clamped straight to the live position -- audibly, the engine sound would arrive instantly instead of staying delayed. Playback position now can't advance faster than real time, so a supersonic approach correctly makes the backlog of engine sound queue up and arrive once it physically can, instead of leaking through early.
- **Doppler warbling on missile motor sound fixed**, same underlying cause and fix as the earlier engine warbling: the position update comes from the missile's physics tick rather than every rendered frame, which read as a noisy velocity signal to Unity's automatic Doppler. Smoothed the same way.
- **Gun spool-up sound repeating mid-burst, root-caused and fixed.** The `[GunLoopDiag]` logging added previously caught it: right after a loop's brief tracking entry expires, a quick trigger re-press could call the gun's sound hook two or three times back-to-back while the game's own "time since last shot" field still reflected the *previous* burst for the first couple of calls. Whether to play the spool-up bang was decided by a separate check *before* registering the new loop, so each of those calls independently saw "no loop yet" and played its own spool-up bang. That decision and the registration now happen as a single atomic step, so only the first of any such back-to-back calls can ever conclude "this is new."
- **Engine volume/pitch could get stuck for several real seconds after a camera cut** (toggling cockpit/external view, a freecam tool cutting back to the cockpit). The supersonic-arrival fix above (playback position can't advance faster than real time) assumed the listener only ever moves continuously; a camera cut instead teleports it, changing the live delay by seconds in one frame, which that clamp mistook for an impossible supersonic overtake and throttled to catching up in real time. Camera position jumps of more than 300m in a single frame (impossible for continuous motion, even trailing a very fast jet) now reset the clamp instead of fighting it, so engine sound snaps to the correct distance immediately after a cut.
- **Missile sonic boom sounding "strange," root-caused and fixed.** `[BoomDiag]` logging showed the same missile triggering the boom twice within 1-2 seconds, at very different distances. Vanilla's own Mach-cone check has a short-range override that always counts a unit as "in the cone" once it's within its own blast radius, on top of the ordinary directional angle test -- a real aircraft rarely satisfies both within seconds of each other (its separate supersonic passes are naturally spaced out), but a missile closing on or flashing past the camera can trip both in quick succession. Since every trigger also played our own double-crack, one missile shot could produce up to four cracks instead of one. A short per-unit cooldown now suppresses a retrigger within 1.5s of the previous one, well under the gap between genuinely separate passes.
- **Missile sonic boom no longer double-crack.** A missile's bow-to-tail gap is tiny relative to an aircraft's (proportional to its much shorter length) -- too tiny for the double-crack to read as a real N-wave, instead sounding like a stutter/bug. Missiles now play a single, clean crack, cut short right after it starts (same tail-truncation trick as the aircraft's bow shock) so the pitched-up clip reads as a sharp snap instead of a lingering boom tail.
- **Aircraft sonic boom's double-crack no longer sounds like a muddy echo.** Both copies of the boom clip previously played out in full, only ~0.1s apart -- two overlapping full-length copies of the same sound reads as a bad echo rather than a crisp bow/tail double-crack. The first (bow shock) copy is now cut short shortly after it starts instead of ringing out, so the second (trailing shock) copy is the one that actually plays out cleanly in full.
- **Engine sound noticeably trailing an aircraft during a close, fast flyby, partly addressed.** Two separate things stack here: the actual propagation delay legitimately makes a fast source's sound trail its visual position on a close pass -- the real effect of a jet's roar lingering behind it, most pronounced approaching/departing a nearby camera at trans- or supersonic speed, and not a bug (same category as the gunfire duration compression kept earlier). On top of that, though, the Doppler-warbling fix's position smoothing (a fixed 0.15s time constant, chosen for the typical case) adds its own non-physical lag whose apparent size scales with the listener's angular rate -- negligible at ordinary distances, but large right as a fast source passes close by. That smoothing now tightens toward near-instant at close range and eases back out to the original value past a few hundred meters, removing its contribution without reintroducing the Doppler noise it was added to fix (which only mattered at the longer ranges where this leaves it unchanged). The remaining trail during an actual close supersonic pass is the real propagation-delay effect described above.
- **Gun sustained-fire loop repeatedly clunking mid-burst, confirmed and fixed.** Confirmed audible, as suspected: a weapon's stop-detection gap check was comparing time-since-last-shot against that weapon's static `fireInterval` field, which doesn't reliably reflect its real firing rate (e.g. a rotary cannon still spinning up) -- when the two diverge enough, every inter-shot gap looks like a stop, re-scheduling the delayed "stop" one-shot on nearly every shot instead of once at the true end. The check now compares against the weapon's own observed shot-to-shot interval (tracked live, updated every real shot) instead of that field, with a 1.5x margin for normal jitter.
- **Missile motor sound now gets the same distance-scaled position smoothing as engines.** The close-flyby trailing fix above only touched engine clones; missile clones used the same kind of Doppler-warbling-safe smoothing but with the original fixed 0.15s time constant, so a missile flashing past the camera up close was exposed to the same non-physical extra lag engines had. Both now share one function for this, so a future tweak to the near/far smoothing values only needs to happen in one place.
- **Gun loop could get stuck on briefly, or skip its startup bang, around a camera switch.** Two compounding causes. First: `Gun.ShotSound()`'s own Prefix mirrors vanilla's `attachedUnit.displayDetail < 1f` gate, which drops to near-zero the instant the camera stops following that aircraft (switching to another unit, say) if it's more than ~1km from the new camera position -- and returns before ever reaching our tracking, so a still-firing gun's loop entry would sit frozen with no way to know firing had actually stopped, or whether a later resume was a continuation or a fresh burst deserving its own startup bang. The loop is now dropped immediately when displayDetail says "not in detail," so it always starts clean the next time a real shot from that gun reaches us. Second, smaller effect: the self-measured firing cadence added above updated by fully overwriting itself with the latest gap every shot, so a single hitch-lengthened gap (a camera cut can itself cause a frame hitch) right before the trigger was released could inflate the stop-detection threshold for that burst's entire tail. It's now blended in a fraction at a time instead, capped against doubling in one step.
- **PCR double-tap toggle silently never worked.** `[PcrDiag]` logging showed the tell: zero rising-edge ticks logged all session despite flares clearly firing repeatedly, meaning `Tick()` never ran even once. Root cause: the driver's `GameObject` was created and `DontDestroyOnLoad`'d directly from `Plugin.Awake()`, which doesn't reliably survive this game's very early bootstrap scene transition (the same failure mode hit once before with a HUD Canvas -- object destroyed a couple seconds later with zero `Update()` calls in between). Fixed by attaching the driver component to the BepInEx plugin's own `GameObject` instead of creating a separate one -- that one is already guaranteed to persist correctly.
- **No chaff observed in-game despite `ChaffEjector`/`RadarChaff` code existing and being patched -- root-caused.** Confirmed via the game's own asset files that chaff has no shipped 3D content anywhere (`ChaffEjector`/`RadarChaff` only appear in Unity's script-metadata table, never alongside real modeled-content names the way `FlareEjector` does, and no `chaffPrefab` asset reference exists at all) -- it's fully-implemented, patchable code with nothing behind it in this build. Our chaff patches are harmless no-ops until/unless that ever changes.
- **One-shot delayed sounds (gunfire bangs, bullet impacts, ejection seat, crash fireballs, countermeasure thumps, the sonic boom trigger) assumed the listener stood still for the whole wait.** Their delay was computed once, from the listener's distance at the exact instant the sound was triggered, then just counted down that fixed amount of real time regardless of what the listener did afterward -- normally still flying. Closing on the source should make the sound arrive sooner than that snapshot predicted; receding should make it arrive later, or (faster than the speed of sound) never. The continuous systems (engine hum, gun loop, missile motor) already recomputed this every frame and were unaffected. One-shots now do the same: since the emission point itself is fixed, each pending sound rechecks every frame whether enough real time has passed for it to have reached the listener's *current* position, instead of trusting a stale precomputed value. A one-shot the listener has permanently outrun is dropped after 60s rather than sitting in memory forever.
- **Afterburner roar (and, less noticeably, everything else engine-related) heard instantly during ordinary fast flight, not just camera cuts -- root-caused and fixed.** The always-on logging added to investigate this caught the real mechanism immediately: every "camera teleport" detected during normal flight was a suspiciously exact ~1000-1200m jump along a single axis, coinciding with dozens of unrelated engines across the entire scene resetting simultaneously. That's `FloatingOrigin.OriginShift` -- the game's own periodic scene re-centering, which "happens routinely at combat speed" (already noted in this file's own comments for why engine history is stored origin-relative) -- not an actual camera cut. The camera-teleport detector compared raw `transform.position` frame to frame, which jumps by the shift amount even though the camera never moved at all, so ordinary fast flight was constantly (falsely) tripping the teleport-reset and defeating the supersonic-overtake clamp on every shift, letting sound leak through instantly far more often than just at real camera cuts. Fixed by comparing positions in `Datum.origin`-relative space instead, exactly like engine history already does, which is naturally stable across a shift and only fires for genuine listener repositioning.
- **PCR started pulsing ECM (or whatever else was selected) instead of the flares it was turned on for.** PCR fired through `CountermeasureManager.DeployCountermeasure`, which always targets whatever's currently *selected* -- switching the HUD selection to ECM while PCR was running redirected PCR onto it too, which was never the intent. PCR now locks onto whichever countermeasure was active *at the moment it was toggled on* and fires that one directly from then on, regardless of what gets selected afterward -- switching to ECM lets ECM behave completely normally (manual control, its own HUD display) while PCR keeps quietly dispensing flares in the background. The manual-fire lockout and the "PCR" HUD label now only apply while the current selection actually matches what PCR is dispensing, not unconditionally.

### Performance
- **Engine sound history was using a `List<T>` as a 30-second sliding window, trimming expired entries off the front with `RemoveRange(0, n)` every single frame.** That's an O(size) array shift every time (up to ~1000+ elements at a typical frame rate once the window fills), for every tracked engine, every frame, for as long as it's alive -- a real, not hypothetical, cost that scales directly with aircraft count. Replaced with a small ring buffer (fixed-size circular array) where both adding a new sample and dropping expired ones from the front are O(1) -- just moving an index, no data movement.
- **Engine `AudioSource` settings (spatial blend, rolloff curves, min/max distance, etc.) were being re-copied from the real engine to its tracked clone unconditionally every frame**, including 4 curve reads plus up to 4 curve writes through Unity's native interop each time -- guarding against a transient bad-state race that, per the original investigation, only ever matters for a moment right after a clip swap and corrects itself shortly after on its own. An actual clip change still gets an instant, unconditional re-sync (a real `Stop()`/`Play()` has to happen right then regardless); everything else now only re-syncs on a 0.5s periodic safety-net check instead of every frame, cutting that cost by roughly 30x with no change to the fix it was added for.
- **Reported "really bad performance issues" in a busy session -- root-caused to a gap in engine tracking cleanup, found via a dedicated audit.** `TickEngines()` never checked the owning aircraft's camera detail level at all, unlike its gun-loop equivalent (`TickLoops()`), which already tears an entry down the moment its aircraft drops out of camera detail. "Detail" here is only ever 1 for whichever single unit the camera is actively following -- every OTHER tracked engine, once it had ever started, kept paying the full per-frame cost (history sampling, position smoothing, both filter cutoffs) for the rest of its existence regardless, out to the full 20km tracking range, scaling with total live aircraft in the match rather than just the one actually being watched. Fixed by adding the same detail-based teardown `TickLoops()` already had, for the 6 of 8 engine types where the owning aircraft is easily accessible (PropFan's transpiler-based patch and JetNozzle's Afterburner, a value class with no back-reference to its owner, are left as a known small gap). On top of that, `Turbojet`/`Turbofan` specifically never even had the recording-side detail gate `TurbineEngine` already had, so they fed new samples into the above regardless of detail too -- both are two of the most common engine types in the game, and now match.
- **CRAM/SPAAG proximity-fragmentation patch was doing eligibility work for every bullet from every gun in the match, not just CRAM/SPAAG's.** A type check plus a `HashSet` lookup against the bullet's target ran unconditionally before the CRAM/SPAAG-only gate, on the same hot per-bullet-per-tick method `BulletCrackPatch` also runs on; a redundant proximity-range check also ran twice for rounds that did qualify. Reordered so that work only happens once a round is already confirmed to be from a CRAM/SPAAG-eligible gun, and the duplicate range check now reuses one result.
- **A small dictionary in the PropFan audio patch (`PropFanFixedUpdatePatch._pendingVolume`) was never cleaned up**, permanently retaining a slot and a dead `AudioSource` reference for every distinct PropFan engine that had ever fired, for the rest of the process's lifetime. Now removed right after its one same-frame use instead of left to accumulate.
- **Removed a leftover temporary diagnostic** (`CockpitToggleDiagPatch`, logging every `Aircraft.SetCockpitRenderers` call) that was never cleaned up after the investigation it was added for concluded.
- **Performance issues persisted after the engine-tracking fix above -- gated a large amount of leftover per-event diagnostic logging behind a new, off-by-default `Verbose Logging` config option (Diagnostics section).** This mod accumulated a lot of `[XyzDiag]` logging over many past investigations that was never cleaned up once its investigation concluded -- gun loop start/stop/resume transitions, a line for every bullet crack (capped at ~12/sec, but that's still a sustained rate for the whole duration of any fight with automatic weapons firing nearby), engine clone creation/tick diagnostics (including several `AnimationCurve` reads through Unity's native interop that were previously done unconditionally, not just the log line itself), CRAM/SPAAG proximity-fragmentation events, sonic boom triggers, and two always-running scene-wide checks (`FindObjectsOfType<AudioListener>()` every 5s, cockpit-state logging every 2s). None of this was touched by the earlier engine-tracking fix, and in a busy multiplayer session the aggregate volume is real, sustained I/O for the entire fight -- exactly when performance matters most. Left on for one-time startup/warning logs (mod init, embedded resource loading, config registration), which cost nothing during actual play.
- **Added an always-on `[PerfSummary]` diagnostic (independent of Verbose Logging, logged every 10s) reporting tracked-object counts (engines/gun loops/tracked loops/pending one-shots) and this mod's own actual per-frame `Tick()` cost (average/max milliseconds).** Added specifically because guessing at further fixes without real numbers isn't productive -- this will show directly whether the counts are holding steady (confirming the leak/cleanup fixes are working) or still growing, and how much of a frame this mod's own systems actually cost, which either points at a specific remaining issue here or rules this mod out as the cause entirely.
- **Found the actual "performance disaster" via the new `[PerfSummary]` log, and root-caused it -- an uncapped object-creation storm on bullet IMPACT sounds, the untreated twin of the bullet-crack storm bug fixed earlier.** Real log data showed `pendingOneShots` climbing into the thousands and `Tick()` cost rising from ~0.001ms to 20+ms within seconds, during heavy sustained automatic gunfire. `ImpactEffectPlayPatch` -- the single choke point for every bullet impact sound (ground/armor/water/self-destruct, from every gun in the game) -- had zero rate limiting at all, unlike bullet cracks (already capped after the original CIWS-cannon-firing-2700-rounds-in-10-seconds incident): a rotary cannon or CIWS firing hundreds of rounds/second into water or a target scheduled hundreds of brand-new `GameObject`+`AudioSource`+filter-chain allocations per second, and several such guns firing at once (a missile-swarm engagement, say) compounds directly. Capped to ~30/sec globally, looser than the crack cap since impact sound is more central to combat feedback -- a dense stream of impacts also physically blurs into one continuous sound in reality anyway, same reasoning as the crack cap. The visual particle effect is completely unaffected either way; only the delayed-sound scheduling is skipped when throttled.
- **Root-caused a "weird high-pitched distortion" on PropFan engine sound at low RPM, present in both the interior and exterior clips.** This user's config runs with `Engine Sound Propagation` off, so PropFan's engine audio was going entirely through the lightweight direct-on-real-source cockpit filter path -- which had been silently inert on this source until the `AudioSource.bypassEffects` fix a few versions ago made it actually run for the first time. That exposed a real, pre-existing bug: this mod's filter Resonance setting (2.5 by default, shared by every lowpass/highpass filter it manages) was being applied even when a filter's cutoff sat at its own "fully open" edge (22000Hz for lowpass, 10Hz for highpass) -- a resonant (Q>1) filter still rings audibly right at its cutoff even there, and a peak parked near 22kHz (close to the top of human hearing) is heard as a persistent high-pitched whine. It's normally masked by a loud, broadband engine at high RPM, but PropFan's own volume drops sharply at low RPM, exposing the constant-amplitude ring against the now much quieter fundamental. Fixed everywhere this mod sets either filter's resonance (one-shots, gun loops, engines, tracked loops, and the cockpit-only path): resonance now resets to Unity's own neutral value (1, no boost) whenever a filter's cutoff is at that open edge, and only uses the configured Resonance value when the filter is actually cutting something. Likely fixes the same subtle artifact on other close-range/quiet managed sounds too, not just PropFan -- it was just the easiest place to notice against a sustained, mostly-otherwise-quiet tone.
- **Full-codebase quality sweep (memory leaks, dead code, stale comments, Harmony field-injection correctness, avoidable per-frame work) -- came back clean apart from three real allocation hotspots.** Every collection this mod maintains has a real cleanup path (verified again, including everything added this session); no dead code, no lingering references to config classes deleted in the recent ConfigManager restructuring, no stale `.Value` access on the fields converted to `const`; and every single `___fieldName` Harmony injection and `[HarmonyPatch]` target across the whole mod was cross-checked against a fresh decompile of the actual shipped game DLL, with zero mismatches. Three real, fixable costs found: `JetNozzleAudioEffectsPatch` was rebuilding its thrust+afterburner sibling array (a fresh array plus a reflection `GetValue` per afterburner) from scratch every physics tick; `GroundVehicleEngineSoundPatch` was allocating two fresh single-element sibling arrays every `Update()`; both now cache their sibling list once per instance (`ConditionalWeakTable`) instead of rebuilding it every tick, since the underlying fields never change identity after spawn. Landing gear's own sibling arrays (already using this pattern implicitly via inline `new[] { ... }` literals) got the same per-instance caching for consistency, via a small shared `LandingGearSiblingCache`. Separately, `ComputeCockpitLowpassCutoffOnly`/`ComputeCockpitHighpassCutoffHz` -- called by every `ApplyCockpitOnlyLowpass` invocation (a dozen-plus call sites) plus every engine/loop tick, every frame, but depending only on global state (config, camera view, ejection/airframe blends), never on which source is asking -- are now cached per rendered frame (`Time.frameCount`), so all of those calls within the same frame share one computation instead of each repeating it independently.
- **New config option: `Engine Audio Speed-Of-Sound Delay` (Performance section, default on).** Engines are by far the heaviest part of this mod (continuous per-frame tracking for every engine on every aircraft) -- turning this off falls back to vanilla's instant, undelayed engine/afterburner/thrust audio with zero ongoing tracking cost, while everything else the mod delays (gunfire, missiles, sonic booms, countermeasures, impacts, ejection seat, fireballs) is completely unaffected. Toggling it mid-flight is handled cleanly in both directions -- switching off immediately tears down any already-tracked engine clones (so it can't leave a stale clone playing alongside the now-unmuted real source), and switching back on picks every engine back up fresh the next time it updates.

Entries in this category now carry an explicit ConfigManager display order (`Enabled` → `Auto-Gain` → `Phosphor Color` → `Speck Count` → `Transition Animation`) via a small `ConfigurationManagerAttributes` helper (same technique KaceyTronic-RWR already uses) instead of ConfigManager's default alphabetical-within-section sort, which would otherwise scatter these five in a different order than they're meant to be read in. The saved config file was hand-migrated (old `[Enhanced NVGs]`/`[NVG Auto-Gain]` sections replaced with the new `[Night Vision Goggles]` one, carrying over this user's own tuned values for the settings that stayed) rather than left to accumulate as orphaned sections.

### Investigating
- **Random turbine whine reported shortly after spawning on the ground.** Not yet root-caused. Leading suspect: `Unit.displayDetail` defaults to 0 (C#'s default for an unassigned field) until `CameraStateManager` assigns it a real value, and `TurbineEngineAnimatePatch` gates all recording on `displayDetail >= 1` (mirroring the same gate `Gun.ShotSound()` uses, already confirmed to cause real gaps for guns) -- a just-spawned aircraft could have a brief window where this gate is closed for reasons unrelated to actual camera distance, leaving a gap in that engine's history; once it reopens, whatever pitch/volume gets captured first (potentially a startup RPM transient) plays through a freshly created clone with no prior context to smooth against. Added logging (once per engine instance, to avoid spamming for every out-of-detail AI aircraft) for when this gate closes, plus the first recorded pitch/volume whenever a new engine clone is created, to confirm or rule this out next time it's reproduced.
